# Codex 自动化任务中的偏差与修正

本页根据相关翻译会话中的用户消息、Codex 行为及后续回复记录事实，并区分初始要求与后来追加的限制。[提示词原文](prompts.md)逐项目保存，不把这些事后修正合成一条从未实际发送过的提示词。

## 并行翻译被扩展成多级协调

来源会话：《翻译 SGA 1–7 并制作 XeLaTeX 译本》。

用户要求以几十页、语义连续的块分配工作，每个子 Agent 完成一个块后换新会话，避免一个会话反复追加任务、压缩上下文。Codex 在运行中额外引入了四个协调 Agent，把本应由主 Agent 完成的派发、收稿和集成工作再委派出去，占用并发位并增加 token 消耗。

用户原话：

> 我没有让你派发Coordinate这种子Agent,Coordinate消耗了非常多的token,占用了大量并发位置,但同时它们的产出和调度功能本应是你的工作.你应该以token效率为目标,不要搞这种多级子Agent,你直接派发和接受译稿.

随后 Codex 报告停止了四个协调 Agent，把释放出的四个位置直接用于翻译，并改为由主 Agent 接收、集成译稿。该例体现了对“允许并行”的过度扩展：增加调度层并不自然符合用户期望的资源分配方式。

## 子任务结束，OCR 模型进程仍在运行

来源会话：《完整翻译本书并制作 XeLaTeX 译本》（FGA）。

这次任务的初始提示词允许子 Agent 并行，没有禁止本地 OCR。Codex 启动了本地 GLM-OCR。用户随后明确表示不希望运行本地 OCR，并询问是否仍有子 Agent 在做这件事：

> 我希望你不要调度本地运行的OCR模型.你现在是否仍有子Agent在做这件事?

Codex 的当时回复为：

> 有。负责 OCR 的子 Agent 已结束任务，但它启动的本地 GLM-OCR 进程仍在运行。我现在立即停止该进程，后续也不再调用本地 OCR 模型。

随后会话记录了终止该进程、卸载模型的处理。这里既有用户对资源使用偏好的追加澄清，也有任务生命周期管理的问题：Agent 结束不代表它启动的进程已经结束。

后来的 SGA 4½、函子代数几何导论和反常层初始请求，直接加入了不调度 CPU / GPU 占用高的本地 OCR 模型的限制。这一限制是在实际运行反馈后逐步明确的，不能追溯为 FGA 最初已经提出的要求。

## 全文翻译与推断补写原文的边界

来源会话：《翻译 SGA 1–7 并制作 XeLaTeX 译本》。

面对重排本和扫描本均残缺的位置，Codex 曾依据上下文推定缺失字母或指标。例如，报告记录过高度定义中等号后的 `A`，以及公式末尾的指标 `n`。这些推断一度被写入译文。

在讨论如何处理源缺损后，用户的回答原文为：

> 先按缺页处理,翻译结束后给一个缺失内容报告,我会按照你给出的报告去找是否有可补足残缺处的文本.

后续修改记录显示，上述推补被撤回，正文改用缺失标记，并登记原页、译文位置、上下文及已查看的补源。主 Agent 的工作随之收敛为翻译现存内容、汇总补源记录。

这个调整明确了“完整翻译”的范围：数学上似乎能推断出缺字，不等于底本实际提供了该字。用户关于数学译注的要求，也不能自动解释为授权重建无法读取的原文。

## 整理提示词时再次偏离了保存原话的目标

来源会话：《合并纯数翻译项目》。

本仓库初版将历次用户请求改写成一份结构化的“整理版”提示词，把初始要求、后续纠正和 Agent 自拟的实施规则合在一起。这样做丢失了提示词的真实措辞和演变过程，也容易让读者误以为这些要求在任务开始时就全部存在。

用户随后明确纠正：

> 提示词不应该用整理版,应该保留我之前会话的真实提示词.

现改为按七个项目逐字保存实际用户消息，将后续纠正分别列出。附件路径及界面包装省去，用户正文不润色、不重写。

## 如何看待记录中的数学补注

这些经历说明，自动执行期间仍发生过需要用户介入的理解与行为偏差。文档中有原页标记、术语互链、反例或补充论证，并不代表内容已经过人类数学审校。

仓库内译文、公式、图表、术语表和数学 Gap 判断目前尚未经人类仔细核对。既有补注也属于待核查内容；原著勘误、OCR / 转写错误、源文件缺损和新提出的数学疑点应继续分开记录。
